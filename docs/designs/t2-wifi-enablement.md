# Design: T2 Wi-Fi on MacBookPro16,2, and the boot-from-stock-ISO rebase process

Generated by /gstack-office-hours on 2026-10-02
Branch: t2-enablement
Repo: projectbluefin/dakota (fork: Drachemann/dakota-t2)
Status: APPROVED
Mode: Builder

## Problem Statement

On the Apple T2 MacBookPro16,2 (BCM4364B3 Wi-Fi, island `trinidad`) the client
associates to the AP as WPA2-PSK/CCMP and then not one EAPOL frame crosses in
either direction, so the four-way handshake never completes and the supplicant's
own timeout disconnects it. The same chassis, chip, MAC and AP work under a
t2linux Ubuntu install on kernel 7.2.8.

The deliverable is not the image. The T2 image carries Apple radio firmware and
cannot be published, so there is no published T2 ISO. What must work is the
process: boot the **official** Dakota ISO, install to the internal NVMe using
external USB input, then `bootc switch` onto a locally built T2 image that works.

## What Makes This Cool

An abandoned Apple machine becomes a first-class Bluefin target through the same
published artefact everyone else boots, with the T2 work riding as a rebase
rather than a fork of the ISO pipeline. The licensing constraint and the
ergonomics constraint point the same way: because the firmware cannot be
redistributed, "stock ISO then rebase" is both the legal route and the one that
keeps a single published image.

The supporting artefact is the diagnostic harness, which turns an unreproducible
"Wi-Fi is broken" into a verdict-first report, with a separate table of
signatures that are expected noise on this chassis because they were confirmed
identical on the reference t2linux install.

## Constraints

- Never write to any `ublue-os/*` repository.
- An image carrying Apple firmware must not be published; the fork's ghcr free
  tier also fails on quota (500 MB storage, 1 GB transfer/month).
- The user runs builds, exports and flashes. Hand over command sequences.
- `just validate` and `just export` require `umask 022`.
- BuildStream elements are the only build mechanism. No dnf, rpm-ostree, COPR,
  Containerfile overlays or post-build package installation.
- Never push directly to `main` or `testing`.

## Premises

1. The deliverable is a process, not a published T2 image. Forced by the firmware
   licensing posture `elements/bluefin/t2-brcm-firmware.bst` lines 31-42
   documents, not by preference.
2. The next action is not a build. Both remaining variables are testable live, on
   hardware already owned, in about a minute each.
3. `v7.2.7` is not a Wi-Fi target. `v7.2.8` is.
4. The harness's firmware-staging mechanism is obsolete, not merely buggy, so it
   should be repointed rather than patched in place.

### Where the override is mounted, and why the obvious target does not exist

`/lib/firmware/updates/brcm` is the route `docs/t2-diagnostics.md:100-111`
recommends, and it is correct **on the Ubuntu reference**, whose root is writable.

It is **not available on the image**: `/lib` is a symlink to `/usr/lib`, and on
bootc `/usr` is a read-only mount inside the deployment, so
`mkdir -p /lib/firmware/updates` fails and there is no mount target.

Two working forms, chosen per target:

| target | override form |
|---|---|
| the image (cell B) | `sudo mount --bind "$STAGED" /usr/lib/firmware/brcm`. The directory already exists (the element creates it) and a bind mount over a path inside a read-only mount is permitted. This replaces the whole `brcm` directory with the staged set, which is what the A/B wants since both sets are complete for this chip. |
| the Ubuntu install (cell D) | `sudo mkdir -p /lib/firmware/updates/brcm && sudo mount --bind "$STAGED" /lib/firmware/updates/brcm`. Root is writable, and `updates/` is searched first. |

Both are reverted with `umount`, and neither uses `alternative_fw_path`, so the
absolute-path defect that voided the previous three attempts does not arise.

**Pre-flight check, required before believing either result:** confirm the target
directory exists and is non-empty after the mount (`ls "$TARGET" | head`), then
confirm the `Firmware: BCM4364/4` revision line changed (see The Assignment).

## Decision 1: blob, kernel, or both

**Neither yet. Both variables are testable live, so run the 2x2 first.**

The previous session treated the firmware A/B as needing the image and the kernel
as needing a build. Neither does: the override is a bind mount.

| cell | kernel | firmware | route | status |
|---|---|---|---|---|
| A | 7.2.6 (image) | 2024 kansei | stock image | known FAIL (inherited) |
| B | 7.2.6 (image) | 2023 macOS | bind mount on the image | untested, ~1 min |
| C | 7.2.8 (t2linux) | 2023 macOS | stock Ubuntu install | known PASS (inherited) |
| D | 7.2.8 (t2linux) | 2024 kansei | bind mount on the Ubuntu install | untested, ~1 min |

Reading it, stated at the resolution the matrix can actually support — it varies
**kernel version and firmware bytes only**:

- **B pass** → the firmware bytes are causal and the kernel version is irrelevant
  to this failure. Fix is a firmware re-source.
- **B fail, D pass** → kernel **version** matters. This does not separate version
  from config, because cell D runs Ubuntu's `brcmfmac` and config, not fdsdk's.
  The kernel-versus-config question is explicitly deferred to the separate
  deployments in Decision 2(b); do not read a D pass as naming the mechanism.
- **B fail, D fail** → 2024 is bad on both kernel versions and 2023 is
  insufficient on 7.2.6, so both must change.
- **B pass, D fail** → interaction; both.

Run **B first**. Test the hypothesis whose fix you least want to need: if the
answer is "the firmware", the fix is architecturally expensive, because the
working set is macOS-extracted and the element header (lines 23-42) establishes
there is no redistributable path and no upstream `WHENCE` entry. If the answer is
"the kernel", the fix is a one-line ref bump.

**Do not bump to `v7.2.7`.** Bumping to "match the series' KVER" is a full kernel
rebuild that moves nothing on the radio, because 7.2.7's `brcmfmac` is
byte-identical to 7.2.6's. The target is `v7.2.8`. Moving the kernel also requires
re-pinning `patches/linux/3001-applesmc-convert-static-structures-to-drvdata.patch`
to the series' main revision, which `elements/core/linux-fdsdk.bst` lines 16-20
hold one revision back (`fea007484b84`) precisely because the element pins v7.2.6.

Mechanism caveat, and it bears on how much weight the lead carries:
`c5f73cde72` fixes a **TX-completion race** that delays key installation. The
observed signature is **RX EAPOL-Key=0** — message 1 of the four-way handshake
never reaches the supplicant. A lost TX-completion wakeup does not obviously
produce that. Strong, named, version-exact lead; not a proven cause. Cell D
settles it empirically.

**Third candidate the matrix cannot see:** the `CONFIG_CFG80211=m` /
`CONFIG_MAC80211=m` demotion plus `FW_LOADER_COMPRESS_ZSTD=y`, added by
`files/linux/fdsdk-config.sh` (the `remove`/`module` pair) and asserted by
`elements/core/linux-fdsdk.bst:177-178`. Ubuntu does not have `cfg80211` in that
shape, `cfg80211`'s init ordering is exactly what changed, and that ordering sits
on the regulatory and EAPOL path. A built-in/module decision cannot be changed at
runtime, so no live test reaches it. This is why kernel version and kernel config
must be separate deployments.

**Confidence.** The four hypotheses below are mutually exclusive and exhaustive
over "what makes Wi-Fi fail on this image", and sum to 1.00:

| hypothesis | prior |
|---|---|
| Kernel version or kernel config alone is sufficient (firmware irrelevant) | 0.30 |
| The vendored 2024 firmware bytes alone are causal (kernel irrelevant) | 0.35 |
| Both must change | 0.25 |
| Neither explains it (third cause) | 0.10 |

The prior handoff had the firmware at 40-50%. The re-weighting initially rested on
the named 802.1X commit landing in exactly the release the working install runs,
plus a firmware delta described as "75 bytes of version/date/FWID strings out of
820,013 in `trinidad.bin`". **That description was incomplete and the re-weighting
was wrong.** Measured directly, file by file, between the two sets:

| file | 2023 | 2024 | difference |
|---|---|---|---|
| `...trinidad.bin` | 820,013 | 820,013 | 75 bytes — version, date, FWID strings |
| `...trinidad.clm_blob` | 35,322 | 35,478 | **29,543 bytes differ (83%), size changed** |
| `...trinidad.txcap_blob` | 723 | 723 | 17 bytes |
| `...trinidad-HRPN-{m,u}.txt` | — | — | identical |

The `.bin` delta really is only strings. The **CLM blob is a different build**: it is
the Country Locale Matrix, the per-domain channel and power data the firmware uses,
and it is the largest content difference between the working and failing
configurations. A version-string delta argues the firmware sets are
interchangeable; an 83% CLM delta does not. The priors above reflect that
correction and put the firmware back ahead of the kernel, reversing this document's
earlier position. `docs/t2-diagnostics.md` now carries the same table so the
misreading cannot recur.

**What would falsify the "firmware is causal" reading:** a cell B failure together
with a cell D pass, which would leave kernel version as the whole story.

These are priors; the matrix replaces them.

## Decision 2: iteration route

Keep the architecture. It is forced, not chosen: the image carries Apple
firmware, so it cannot be published, so there is no published T2 ISO, so the
deliverable is "official ISO → rebase".

**(a) Transfer cost. The originally proposed cache-skip does not work — measured.**

The proposal was a persistent `oci:` layout on the USB with `podman push`, on the
assumption that it skips blobs whose digests already exist. **It does not.** A
271 MB image with a 250 MB layer, pushed twice to the same layout under two tags:

```
PUSH #1 (cold layout) wall=2.31 s   Copying blob sha256:2cfe8ee4… , 74d97c42…
PUSH #2 (same blobs, new tag)  wall=2.26 s   Copying blob sha256:2cfe8ee4… , 74d97c42…
layout: 4 blobs, 254M on disk
```

Same wall time, same `Copying blob` lines. The layout deduplicates on disk (4
blobs for two tags) but **re-writes every blob on every push**, so the full image
would cross USB every iteration — the ~21 min/iteration problem the layout was
supposed to solve. (The same probe was first run on a 2 KB image, where timing
cannot distinguish the cases; that run was inconclusive and is why the 271 MB run
was done.)

Consequence: at the ~6.5 MiB/s the SanDisk stick measured, a 4 GiB image is ~10.5
min of USB write plus ~10.5 min of USB read on the T2.

**Corrected after the review, with the media physically present.** That premise was
wrong: it inherited the handoff's claim that the stick was the only remaining media.
Two 931 GB external HDDs are attached — `/dev/sda1` at `/media/matt/StayHuman` with
337 GB free, and `/dev/sdb1` at `/media/matt/FereterCopy` with 21 GB free — and a
`dd` with `conv=fsync` measured **24 MB/s** sustained write, about 3.7x the stick. A
4 GiB image is therefore ~3 min of write and roughly a minute of read: about **4 min
per iteration**, not 21. The transfer route is not the blocker this section
describes, and the `oci:` dedupe failure above is a nice-to-have rather than
Decision 2's first task. Stage on `StayHuman`, not `FereterCopy`.

**Fallbacks, in the order worth trying** (each judged by the pass criterion
below):

1. **`rsync` the blob directory.** On the build host, `podman push` to a *local*
   staging layout (local disk, fast), then
   `rsync -a --ignore-existing <staging>/blobs/ <usb-layout>/blobs/` and copy
   `index.json` and `oci-layout` across. `--ignore-existing` skips blobs already
   on the USB, so only the changed layer is written. `rsync` is built for exactly
   the decision `podman push` declines to make. Note this fixes the **write**
   half only.
2. **A local OCI registry on the build host, pulled over the phone hotspot.**
   Registries support blob existence checks properly, and this removes the USB
   from the loop entirely. It needs no publishing: a `registry:2` container on the
   build host is not ghcr and has no quota. Requires both machines on the same
   network (the hotspot), and `--tls-verify=false`.
3. **`podman save --compress`** to cut bytes at the cost of CPU, if 1 and 2 both
   disappoint.
4. **Faster or larger media**, which is a purchase rather than a fix.

**Pass criterion for whichever route is tried:** push/pull one image twice with
only one changed layer, and require that the second transfer's wall time scales
with the *changed layer only* — concretely, that it is closer to the size of the
new layer than to the size of the image. A run in which the second transfer takes
substantially the same time as the first is a **fail**, which is what the `oci:`
layout just produced. Record both wall times.

**(b) One variable per deployment.** bootc keeps prior deployments, so on-machine
A/B is free — but only if each switch differs by one thing. Kernel **version**
(`v7.2.8`) and kernel **config** (the `cfg80211 =m` demotion) must be separate
deployments, or a result attributes neither. Never bundle kernel, firmware and
harness changes into one image.

**(c) Network, TLS, and recovery are three separate questions.**

*The switch-and-boot loop needs no network.* Per step:

| step | host | needs network? | needs TLS / correct clock? |
|---|---|---|---|
| Building the image | build host (has network) | yes, for source fetching | build host's own clock |
| `podman push`/`rsync` to USB, `podman load`/`pull` on the T2 | both | **no** | **no** |
| `bootc switch --transport containers-storage` | T2 | **no** | **no** |
| cells B and D (firmware bind mount) | T2 | **no** | **no** |
| Local-registry fallback (route 2 above) | T2 | yes (hotspot) | no, with `--tls-verify=false` |
| Installing `dsh` on the T2 | T2 | yes | **yes** — npm/GitHub over TLS |

*`dsh` is a convenience, not an acceptance requirement.* It is the agent harness
that lets the machine be driven over the tether instead of by hand at the
keyboard. Nothing in A1-A5 depends on it. So the tether is not required for the
switch to work, and it is not required for acceptance.

*An out-of-band recovery path is a precondition for the first `bootc switch` — as
a safety gate, not a network gate.* A T2 running a bad kernel has no internal
keyboard, no trackpad and no Wi-Fi, so without an independent way onto the machine
a failed switch cannot be recovered in place. This is about recoverability. It is
independent of the table above: the switch needs no network, and the recovery path
is required regardless.

Recovery pass criterion, tested on the **stock** deployment before the first
`bootc switch` (it is driven with the same external USB keyboard and mouse A1
already requires):

- Hardware: external USB keyboard and mouse; the phone with USB tethering
  enabled, connected directly to a USB-C port.
- Observe: `ip addr` shows a USB network interface (CDC-NCM/RNDIS) with a DHCP
  lease; `ping -c3 <the phone gateway>` succeeds; `timedatectl` reports the clock
  synchronised and the date is no longer 2011.
- Pass = all three. On pass, the machine is recoverable without its internal
  input devices, and the first `bootc switch` may proceed.
- Fail = the phone's tethering class is not bound by the stock kernel. Fallback is
  a USB Ethernet adapter; if that also fails, do not `bootc switch` until some
  other out-of-band path exists.

Also keep the stock deployment as a permanent rollback target and keep external
USB input until acceptance.

## Decision 3: acceptance, and what to re-run

### Acceptance

- **A1** From the official published Dakota ISO, with only external USB input,
  install to the internal NVMe; load the built T2 image; `bootc switch`; reboot;
  reach a desktop where the internal keyboard and trackpad work and Wi-Fi carries
  real traffic.
- **A2** The same from a **cold install**. A passing cold install produces
  something A1 cannot: proof that the process works for a machine that has never
  had the T2 image, which is the actual user story. A1 can be satisfied by a
  machine already carrying the T2 kernel in a prior deployment, so it proves the
  upgrade path only. A2 is where the stock ISO's own kernel, installer and
  partitioning are exercised for the first time on T2 hardware.
- **A3** Every assertion-bearing check BD emits holds, named as BD emits them:
  boot completed, `bluefin-swapfile-init`, regulatory.db loaded, cfg80211 is a
  module, BT advertising (patch 9002), **wifi-assoc**, **wifi-handshake**,
  **wifi-payload**, boot media integrity, ALSA devices present, no failed units.
  That is **eleven** checks, because the single circular `Wi-Fi connected` check
  (BD:240) is replaced by the three staged Wi-Fi checks in the next section.
  Eight have been observed green on the T2 (the non-Wi-Fi eight, minus the
  qualification in the next paragraph); the three Wi-Fi checks are the target and
  have never been green. A3 means "eight stay green and the three turn green".
  **`no failed units` is required unqualified at acceptance** — zero units failed,
  network-dependent ones included. The qualified reading ("beyond
  network-dependent ones") applies only to the pre-Wi-Fi baseline, and is
  discharged by the wireless target and `NetworkManager-wait-online` reaching
  `active` once Wi-Fi works; record `systemctl --failed` verbatim either way.
- **A4** `bootc rollback` returns to stock, and switching forward works again.
- **A5 non-goal** Bluetooth `BCM.hcd`. **Downgraded claim:** no redistributable
  source is known. `elements/bluefin/t2-brcm-firmware.bst` lines 124-126 assert

### Per-iteration check set, and its cadence

**Run `scripts/t2-boot-diagnostics.sh` once.** One pass emits every check result.
Typical cost is about 30 s; budget up to about 150 s when boot-media integrity has
an inode to resolve, since that single check carries a `timeout 120`.

**Cadence governs adjudication, not execution.** The pass always runs and always
prints all results. What differs is whether a *change* in a result is actionable
this iteration:

| check class | adjudicate |
|---|---|
| the eight non-Wi-Fi checks except the subject-dependent ones below | every iteration |
| boot media integrity | once per new flash **or new deployment** (a `bootc switch` changes the composefs objects) |
| BT advertising (patch 9002) | when the kernel or the 9002 patch changes — so **every iteration of a kernel bump** |
| ALSA devices | when audio elements change |
| `bluefin-swapfile-init` | when `bluefin-swapfile-init` changes |

Readings that are unchanged from the previous iteration are recorded, not
re-litigated.

### The Wi-Fi check is circular today and must be replaced

BD:240 asserts `nmcli -t -f GENERAL.STATE dev show wlp229s0` contains
`100 (connected)`. Association is exactly what already succeeds, so that check
cannot distinguish this bug from a working radio. Replace it with three checks:

| new check | signal and command | pass condition | where it goes |
|---|---|---|---|
| `wifi-assoc` | `nmcli -t -f GENERAL.STATE dev show <iface>` | contains `100 (connected)` | exists as BD:240; rename |
| `wifi-handshake` | `wpa_cli -p "$RUNDIR" -i "$IFACE" status` for `wpa_state`, plus `grep -ac 'RX EAPOL-Key' "$RUNDIR/wpa.log"` and `grep -ac 'TX EAPOL-Key' "$RUNDIR/wpa.log"` | `wpa_state=COMPLETED`. The two counters are diagnostic and are recorded verbatim: the observed failure is `RX EAPOL-Key=0 TX EAPOL-Key=0`, and `RX>0` with association but no completion is the different signature "AP is talking, key exchange failing" | the `wpa_cli status` and `wpa.log` capture exists in RT:166-188; **add** the same three readings to BD |
| `wifi-payload` | `curl -fsS --max-time 15 http://detectportal.firefox.com/success.txt` and compare the body to `success` | exit 0 **and** body exactly `success` | **add** to BD as a new check |

Two deliberate choices in `wifi-payload`: it is **plain HTTP**, so the T2's
pre-NTP 2011 clock cannot fail it on certificate validation and confound a Wi-Fi

distinguishable failure rather than a silent non-zero. It requires internet, which
is what "carries real traffic" means; when Wi-Fi is the variable under test the
tether must therefore be disconnected or the check would pass over the tether —
record which interface carried the request.

## Approaches Considered

### Approach A: Matrix first, then single-variable builds (chosen)

Run cells B and D, read the result, then build the confirmed cause as **one
variable per deployment**: if the matrix implicates the kernel, deployment 1 is a
version-only bump to `v7.2.8` with the config untouched, and only if that leaves
the config candidate live does a second, config-only deployment follow. So the
matrix costs no build, and the build cost is **one kernel build if the version is
the whole story, two if it is not**. Effort S for the matrix (human ~15 min), then
1-2 kernel builds at ~20+ min each including transfer. Risk Low. Reuses the
existing bind-mount technique and the existing check set.

### Approach B: Kernel to v7.2.8 only

Bump `core/linux-fdsdk.bst`, re-pin patch 3001, build once. Effort M (one kernel
build plus transfer, ~20+ min). Risk Med. Shortest path to the reference version,
but a failure teaches nothing about the firmware, and the `cfg80211 =m` config
candidate rides along invisibly — so a success does not attribute version against
config either.

### Approach C: Both in one build

Kernel to v7.2.8 and a firmware source swap in a single image. Effort L. Risk
High. Highest single-shot probability, but a success is unattributable and it
adopts a firmware change whose redistribution path the element establishes does
not exist — a licensing decision that is hard to reverse once the branch depends
on it.

## Recommended Approach

**Approach A.** The matrix is free in money, time and build cycles, and it is the
only thing that separates the firmware from the kernel before a build is spent. It
also produces something a build cannot: causal attribution that survives a later
regression, so an unrelated failure is not misread as the same one returning. The
residual build cost is one or two single-variable kernel deployments, not one
bundled shot.

Ruled out during the session: bumping to `v7.2.7` (moves nothing on the radio), and
treating either remaining variable as needing a build to test.

## The Assignment

**Fix the transfer route, then run cell B, and record the `Firmware: BCM4364/4`
revision line before and after the bind mount.**

The void-test warning is concrete, because this is how all three previous attempts
failed. Each staged the firmware through `brcmfmac`'s `alternative_fw_path`, and
each died for an environmental reason rather than a radio one:

1. `/etc/firmware` via `modprobe.d` — never read. The boot entry carried no
   parameter and the module parameter stayed empty.
2. `/etc/firmware` via the kernel command line — the parameter applied, and the
   load failed `-2` (ENOENT) for a file that existed.
3. `/var/firmware-alt`, then `/sysroot/state/os/default/var/firmware-alt` — same
   ENOENT, in one case with the run-time check confirming the path resolved.

The cause is that `request_firmware()` always joins the requested name onto its
own search path, so an absolute `alternative_fw_path` becomes
`/lib/firmware//sysroot/...`. The fix is to mount the staged set at a path the
loader already searches — `/usr/lib/firmware/brcm` on the image, whose `/usr` is
read-only, or `/lib/firmware/updates/brcm` on the writable Ubuntu install.

So if the revision line does not change, the override did not take effect and the
test is **void** — do not read it as "the firmware is not the cause". Confirm the
mount is populated and the revision line changed before believing either result.
